## 2. Точные команды сборки и версии

### Подготовка API (из корня исходников ядра, Java 25)

```bash
./gradlew applyAllPatches
./gradlew :purpur-api:publishToMavenLocal
# Windows: gradlew.bat applyAllPatches ; gradlew.bat :purpur-api:publishToMavenLocal
```

Проверить, что `-PpurpurVersion` **действительно читается** сборкой VAC
(в `build.gradle.kts` он читается через `providers.gradleProperty("purpurVersion")`
и печатается задачей `printApiVersion`):

```bash
cd VoidAntiCheat
./gradlew -q printApiVersion -PpurpurVersion=26.2-R0.1-SNAPSHOT
# ожидаемо: [VoidAntiCheat] org.purpurmc.purpur:purpur-api:26.2-R0.1-SNAPSHOT (compileOnly)
```

Без `-PpurpurVersion` подставляется та же версия по умолчанию
(`26.2-R0.1-SNAPSHOT`). Пустое значение отклоняется с явной ошибкой.

Проверить фактическую опубликованную версию (не угадывать):

```bash
ls ~/.m2/repository/org/purpurmc/purpur/purpur-api
```

Ожидается каталог `26.2-R0.1-SNAPSHOT`. Если имя другое — передать его явно:

```bash
cd plugins-src/VoidAntiCheat
./gradlew build -PpurpurVersion="$(ls ~/.m2/repository/org/purpurmc/purpur/purpur-api | grep -v maven-metadata | head -1)"
```

Версии: **Java 25** (toolchain + `options.release = 25`), **Gradle 9.4.1**

```bash
cd VoidAntiCheat

```

Результат: `target/VoidAntiCheat-2.0.4.jar` (версия из `pom.xml`, я её не
менял, чтобы не ломать существующие конфиги/автоматизацию).

Важно: `pom.xml` **не изменён**. Gradle добавлен как второй, эквивалентный
способ сборки под локальный API ядра — по образцу
`purpurbedrock-npc/build.gradle.kts`.

### Версия в plugin.yml и совместимость сборок

Версия в `plugin.yml` теперь **литеральная** (`2.0.4`), как в
`purpurbedrock-npc` и `purpurbedrock-anticheat` этого проекта: ресурсы не
фильтруются, плейсхолдеров в них нет. Это важно по двум причинам:

- в Gradle 9 организация `processResources { expand { } }` устарела, а
  `filter { }` работает нестабильно на многострочных YAML;
- одна и та же версия (2.0.4) используется Maven-сборкой (`pom.xml`),
  Gradle-сборкой и `plugin.yml`, поэтому они не расходятся.

Maven-сборка при этом не ломается: в `src/main/resources` не осталось
`${project.version}`, подставлять нечего.

## 4. Зависимости во время работы

Внутри JAR — только классы VAC (`ru.voidpe.anticheat.**`) и два ресурса
(`plugin.yml`, `config.yml`). API сервера не входит: `compileOnly`, плюс задача
`verifyNoApiInJar` валит сборку, если в артефакт попадёт `org/bukkit`,
`io/papermc` или `org/purpurmc`.

- **Обязательно:** само ядро Purpurbedrock 26.2 (дает `purpur-api`).
- **Мягко (`softdepend`, все через рефлексию, без них плагин работает):**
  `Floodgate` (определение Bedrock-игрока), `Geyser-Spigot` (сессия/устройство
  через внутренний `BedrockPlaceholderHook`), `WorldGuard` (исключение регионов).
- **Опционально, определяется по имени:** `VoidPvP` (признак сервера без
  кулдауна атаки).
- **JVM-флаги не требуются:** `add-opens`/`add-exports`/`Unsafe`/JPMS в коде
  отсутствуют (проверено grep). Доступ к внутренностям ядра — только
  `Class.forName` + рефлексия, с проверкой доступности и безопасным откатом.

### Что именно поправлено в `VoidAntiCheat.java`

1. **Нулевой кулдаун атаки.** Ядро в `Player#attack` ставит
   `attackStrengthTicker = 9999` и `attackStrengthScale = 1.0F` при
   `bedrockCombatEnabled` (по умолчанию `true`). VAC учитывал только плагин
   `VoidPvP` — без него сырой CPS снова считался бы читом. Теперь читается
   флаг ядра **по мирам** (он лежит в `PurpurWorldConfig`, т.е. у каждого мира
   свой — общий `Boolean` был багом, исправлено на `Map<String, Boolean>`).
   Ключ `settings.core-zero-attack-cooldown`.
2. **Неизвестное устройство больше не наказывает.** Reach и AutoClicker
   сравнивали только с `"TOUCH"`. Теперь мобильные ОС, `phone_kbm` и
   **`unknown`** получают сенсорные (мягкие) лимиты; строгие — только
   подтверждённые `windows`/консоли/`KEYBOARD_MOUSE`.
3. **Неизвестный пинг не обнуляет компенсацию.** `getPing()` у Bedrock через
   Geyser часто 0 — это «неизвестно», а не идеальный канал. Ноль обнулял окно
   перемотки и допуск. Добавлен `effectivePing()` и
   `compensation.unknown-ping-assumed-ms: 120`.
4. **Расхождение позиции сервера не считается движением.** `onMove` сверяет
   `event.getFrom()` с запомненной позицией: RTP, дом клана, вход в данж,
   портал, кровать и принудительная коррекция ядром не проходят через
   `PlayerTeleportEvent`. Плюс флаг `unsyncedPosition` после
   телепорта/возрождения/смены мира.
5. **FastBreak не штрафует серверный Бур 3×3.** `VoidEnchants` ломает
   3×3/3×3×2 синтетическими `BlockBreakEvent`, а VAC при `fastbreak-same-tick: 4`
   их **отменял** — бур недоламывал. Теперь происхождение проверяется по PDC
   инструмента (`voidenchants:drill`), подделать с клиента нельзя.
6. **BlockReach согласован с ядром.** Ядро передаёт `bedrockBlockReachTolerance`
   (2.25) в `isWithinBlockInteractionRange` вместо 1.0, разрешая блоки примерно
   до 10 — лимиты VAC масштабируются тем же множителем и пишут предупреждение.
7. **KillAura и группы мобов.** Ядро отключает Java-sweep и даёт нулевой кд, а
   нокбэк усиливает (1.05) → удары по толпе законно расходятся по целям.
   Порог разных целей при включённой боёвке ядра: 5 → 9.
8. **Гибкая настройка без правки JAR:** `/vac check <id> [on|off]`,
   `/vac world list|add|remove|only|clear-only`, маски миров
   (`arena-*`, `*_test`, `lobby?`), `settings.only-worlds`, полное
   tab-автодополнение, справка и `usage` **у каждой команды**.

### Что НЕ изменено

- `pom.xml`, версия `2.0.4`, все 19 проверок, их пороги и буферы по умолчанию.
- Команды `/vac` и алиасы, 22 права, `softdepend`.
- Встроенный Anti-Xray ядра — не тронут (и не дублируется).
- Наказания по-прежнему выключены: `auto-punish: false`, `commands: []`.

## 6. Что именно отключает `enforcement: false`

Проверено по коду, а не по названию настройки. В режиме `false` VAC **только
пишет алерты** и не трогает игрока.

| Место в `VoidAntiCheat.java` | Что делало | При `enforcement: false` |
|---|---|---|
| `flag()` → `return false` | выдача setback/cancel/punish | выключено |
| `setbackRequested` → `event.setTo(safe)` | возврат на безопасную точку | выключено (явный гейт) |
| скачок позиции > `teleport-delta-blocks` | `setTo(from)` | выключено (было **не** загейчено) |
| `BADPACKETS` вне мира | `setTo(clone)` | выключено |
| `blockReachViolation()` | отмена ломания/установки блока | выключено |
| `FASTBREAK` `> лимит + 2` | аварийная отмена | выключено (было **не** загейчено) |
| `FASTPLACE` `> лимит + 2` | аварийная отмена | выключено (было **не** загейчено) |
| Scaffold | отмена установки блока | выключено |
| `setbackPlayer()` (команда `/vac setback`) | принудительный откат | **работает всегда** — это ручная команда админа |

Итог аудита: найдено **3 незагейченных пути** (откат при скачке позиции,
аварийные отмены `FastBreak` и `FastPlace`). Все закрыты единым хелпером
`enforcementEnabled()`; все 9 мест коррекции в файле теперь под гейтом,
поведение при `enforcement: true` не изменилось.

Одно исключение оставлено намеренно: `/vac setback` — явное действие админа,
оно не должно зависеть от режима наблюдения.

**Что это значит на практике:** при `enforcement: false` ни одна проверка
не может телепортировать игрока, отменить ломание/установку блока или
выдать наказание. Единственное, что остаётся, — строки в алертах.

**Чего это не делает:** настройка не отключает сами проверки и не влияет на
Anti-Xray ядра и на `anti-esp` (у последнего свой флаг).

## 7. Риски и ограничения (честно)

1. **Anti-ESP не проверен и по умолчанию выключен** (`anti-esp.enabled: false`).
   Anti-ESP удалённого `PurpurBedrockAC` больше не работает — я **не утверждаю**,
   что VAC его заменяет: это не проверено на клиенте. Модуль использует
   `hideEntity/showEntity`, не трогает пары, где видимостью владеет кто-то
   другой (Vanish), и не трогает игроков с открытым GUI, чтобы не подвесить
   меню на Bedrock. Включать только после теста.
2. **Внутренние классы ядра — не стабильный API.** `PurpurWorldConfig`,
   `World#getHandle().purpurConfig`, `BedrockPlaceholderHook.resolveOnline`
   читаются рефлексией. Если их переименуют, VAC не упадёт: `coreCombatEnabled`
   вернёт «включено» (не считаем частоту ударов уликой), мост устройства —
   `unknown` (мягкие лимиты). Деградация безопасная, но детект слабее.
3. **`blockreach` в текущем конфиге ядра фактически не работает:** при
   `bedrock.anti-ghost-blocks.reach-tolerance: 2.25` ядро разрешает блоки до
   ~10. Ужесточать надо в конфиге ядра, а не в античите.
4. **Нет проверок:** HitBox-расширение, пакетные Criticals, NoSlow,
   InventoryMove/ChestStealer (сознательно — меню `VoidShulker` и Java-меню
   ядра), BedFucker сквозь застройку.
5. **`Timer` ловит ускорение, но не заморозку пакетов (Blink).**
6. **Ложные срабатывания на телефоне** при `inputMode == UNKNOWN` теперь
   смягчены, но порог джиттера `spike-interval-ms: 900` может быть велик для
   мобильного канала 300–600 мс.
