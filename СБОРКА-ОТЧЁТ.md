## 2. Точные команды сборки и версии

### Как это собиралось в CI (воспроизводимая последовательность)

```bash
# 1. исходники ядра 26.2 (zip в main уже с применёнными Purpur-патчами)
git show FETCH_HEAD:Purpurbedrock-arena-16aa0e1c-purpurbedrock.zip > core.zip
unzip -q core.zip -d core && cd core/Purpurbedrock-arena-16aa0e1c-purpurbedrock
git init -q && git add -A && git commit -qm init   # settings.gradle.kts требует .git

# 2. API: появляется paper-api, из него собирается purpur-api
gradle applyAllPatches
gradle :purpur-api:publishToMavenLocal
# -> ~/.m2/repository/org/purpurmc/purpur/purpur-api/26.2-R0.1-SNAPSHOT

# 3. сам плагин
cd compat/VoidAntiCheat
gradle printApiVersion -PpurpurVersion=26.2-R0.1-SNAPSHOT   # доказывает, что свойство прочитано
gradle build -PpurpurVersion=26.2-R0.1-SNAPSHOT
# -> build/libs/VoidAntiCheat-2.0.4.jar

# 4. тест инвариантов enforcement (падает CI при регрессии)
python3 compat/verify-enforcement.py
```

Workflow: `.github/workflows/build-vac.yml`, запуск — push в `arena/**` или
вручную (`workflow_dispatch`). Тот же набор шагов воспроизводится локально.

### Локально на своей машине

Если API уже опубликован в `~/.m2`, достаточно шага 3. Версию не угадывать:

```bash
ls ~/.m2/repository/org/purpurmc/purpur/purpur-api
```

- в Gradle 9 организация `processResources { expand { } }` устарела, а

- одна и та же версия (2.0.4) используется Maven-сборкой (`pom.xml`),
  Gradle-сборкой и `plugin.yml`, поэтому они не расходятся.

Maven-сборка при этом не ломается: в `src/main/resources` не осталось
`${project.version}`, подставлять нечего.

## 4. Зависимости во время работы

Внутри JAR — только классы VAC (`ru.voidpe.anticheat.**`) и два ресурса
(`plugin.yml`, `config.yml`). API сервера не входит: `compileOnly`, плюс задача
`verifyNoApiInJar` валит сборку, если в артефакт попадёт `org/bukkit`,
`io/papermc` или `org/purpurmc`.

- **Обязательно:** само ядро Purpurbedrock 26.2 (дает `purpur-api`).
- **Мягко (`softdepend`, все через рефлексию, без них плагин работает):**
  `Floodgate` (определение Bedrock-игрока), `Geyser-Spigot` (сессия/устройство
  через внутренний `BedrockPlaceholderHook`), `WorldGuard` (исключение регионов).
- **Опционально, определяется по имени:** `VoidPvP` (признак сервера без
  кулдауна атаки).
- **JVM-флаги не требуются:** `add-opens`/`add-exports`/`Unsafe`/JPMS в коде
  отсутствуют (проверено grep). Доступ к внутренностям ядра — только
  `Class.forName` + рефлексия, с проверкой доступности и безопасным откатом.

### Что именно поправлено в `VoidAntiCheat.java`

1. **Нулевой кулдаун атаки.** Ядро в `Player#attack` ставит
   `attackStrengthTicker = 9999` и `attackStrengthScale = 1.0F` при
   `bedrockCombatEnabled` (по умолчанию `true`). VAC учитывал только плагин
   `VoidPvP` — без него сырой CPS снова считался бы читом. Теперь читается
   флаг ядра **по мирам** (он лежит в `PurpurWorldConfig`, т.е. у каждого мира
   свой — общий `Boolean` был багом, исправлено на `Map<String, Boolean>`).
   Ключ `settings.core-zero-attack-cooldown`.
2. **Неизвестное устройство больше не наказывает.** Reach и AutoClicker
   сравнивали только с `"TOUCH"`. Теперь мобильные ОС, `phone_kbm` и
   **`unknown`** получают сенсорные (мягкие) лимиты; строгие — только
   подтверждённые `windows`/консоли/`KEYBOARD_MOUSE`.
3. **Неизвестный пинг не обнуляет компенсацию.** `getPing()` у Bedrock через
   Geyser часто 0 — это «неизвестно», а не идеальный канал. Ноль обнулял окно
   перемотки и допуск. Добавлен `effectivePing()` и
   `compensation.unknown-ping-assumed-ms: 120`.
4. **Расхождение позиции сервера не считается движением.** `onMove` сверяет
   `event.getFrom()` с запомненной позицией: RTP, дом клана, вход в данж,
   портал, кровать и принудительная коррекция ядром не проходят через
   `PlayerTeleportEvent`. Плюс флаг `unsyncedPosition` после
   телепорта/возрождения/смены мира.
5. **FastBreak не штрафует серверный Бур 3×3.** `VoidEnchants` ломает
   3×3/3×3×2 синтетическими `BlockBreakEvent`, а VAC при `fastbreak-same-tick: 4`
   их **отменял** — бур недоламывал. Теперь происхождение проверяется по PDC
   инструмента (`voidenchants:drill`), подделать с клиента нельзя.
6. **BlockReach согласован с ядром.** Ядро передаёт `bedrockBlockReachTolerance`
   (2.25) в `isWithinBlockInteractionRange` вместо 1.0, разрешая блоки примерно
   до 10 — лимиты VAC масштабируются тем же множителем и пишут предупреждение.
7. **KillAura и группы мобов.** Ядро отключает Java-sweep и даёт нулевой кд, а
   нокбэк усиливает (1.05) → удары по толпе законно расходятся по целям.
   Порог разных целей при включённой боёвке ядра: 5 → 9.
8. **Гибкая настройка без правки JAR:** `/vac check <id> [on|off]`,
   `/vac world list|add|remove|only|clear-only`, маски миров
   (`arena-*`, `*_test`, `lobby?`), `settings.only-worlds`, полное
   tab-автодополнение, справка и `usage` **у каждой команды**.

### Что НЕ изменено

- `pom.xml`, версия `2.0.4`, все 19 проверок, их пороги и буферы по умолчанию.
- Команды `/vac` и алиасы, 22 права, `softdepend`.
- Встроенный Anti-Xray ядра — не тронут (и не дублируется).
- Наказания по-прежнему выключены: `auto-punish: false`, `commands: []`.

## 6. Что именно отключает `enforcement: false`

Проверено по коду, а не по названию настройки. В режиме `false` VAC **только
пишет алерты** и не трогает игрока.

| Место в `VoidAntiCheat.java` | Что делало | При `enforcement: false` |
|---|---|---|
| `flag()` → `return false` | выдача setback/cancel/punish | выключено |
| `setbackRequested` → `event.setTo(safe)` | возврат на безопасную точку | выключено (явный гейт) |
| скачок позиции > `teleport-delta-blocks` | `setTo(from)` | выключено (было **не** загейчено) |
| `BADPACKETS` вне мира | `setTo(clone)` | выключено |
| `blockReachViolation()` | отмена ломания/установки блока | выключено |
| `FASTBREAK` `> лимит + 2` | аварийная отмена | выключено (было **не** загейчено) |
| `FASTPLACE` `> лимит + 2` | аварийная отмена | выключено (было **не** загейчено) |
| Scaffold | отмена установки блока | выключено |
| `setbackPlayer()` (команда `/vac setback`) | принудительный откат | **работает всегда** — это ручная команда админа |

Итог аудита: найдено **3 незагейченных пути** (откат при скачке позиции,
аварийные отмены `FastBreak` и `FastPlace`). Все закрыты единым хелпером
`enforcementEnabled()`; все 9 мест коррекции в файле теперь под гейтом,
поведение при `enforcement: true` не изменилось.

Одно исключение оставлено намеренно: `/vac setback` — явное действие админа,
оно не должно зависеть от режима наблюдения.

**Что это значит на практике:** при `enforcement: false` ни одна проверка
не может телепортировать игрока, отменить ломание/установку блока или
выдать наказание. Единственное, что остаётся, — строки в алертах.

**Чего это не делает:** настройка не отключает сами проверки и не влияет на
Anti-Xray ядра и на `anti-esp` (у последнего свой флаг).

### Отложенные действия — проверено отдельно

Автоматических отложенных наказаний в VAC нет, и это не предположение:

- единственный `teleport()` в коде находится внутри `setbackPlayer()`;
- `setbackPlayer()` вызывается **ровно из одного места** — обработчика команды
  `/vac setback` (ручная команда админа);
- периодическая задача `secondTick()` (раз в секунду) не содержит ни
  `setCancelled(`, ни `.teleport(`, ни `runPunishments(` — она только затухает
  VL, сбрасывает чистые состояния и вызывает `timerCheck`, который идёт через
  `flag()` и потому гейтится;
- `runPunishments()` вызывается ровно в одном месте — внутри `flag()`, **после**
  раннего выхода `if (!enforcement) return false;`.

### Это теперь авттест, а не обещание

`compat/verify-enforcement.py` — статический регрессионный тест, который
запускается в CI **до** сборки и валит её при нарушении. 18 проверок:

| Что проверяется | Зачем |
|---|---|
| каждая из 9 точек `setCancelled(true)` / `setTo(...)` под гейтом | новая отмена не проскочит мимо `enforcement` |
| в `flag()` есть ранний выход до любых действий | setback/cancel/punish не выполнятся |
| `runPunishments()` только из `flag()`, после проверки | наказание не может обойти режим наблюдения |
| `teleport()` только в `setbackPlayer()` | нет автоматических откатов |
| `setbackPlayer()` только из `/vac setback` | откат остаётся ручным |
| `secondTick()` без отмен/телепортов/наказаний | нет отложенных действий |

Тест проверен **мутацией**: при возврате старого кода (снятый гейт с отката по
скачку позиции и с аварийной отмены `FastBreak`) он падает с указанием строк.
Отдельно была найдена и закрыта дыра в самом тесте: условие вида
`if (cancel || <другое>)` раньше считалось «под гейтом», хотя второе условие
обходит `flag()` — именно так и работали аварийные отмены.

## 7. Риски и ограничения (честно)

0. **Скомпилировано, но не запущено на сервере.** Успешная сборка доказывает
   только то, что код совместим с API 26.2 и JAR корректен. Ни один игровой
   сценарий в CI не проигрывался — для этого нужен настоящий сервер и
   Bedrock-клиент (раздел 8).
1. **Старый `PurpurBedrockAC` обязательно убрать до установки VAC.** Это не
   формальность: внутри него нет режима «только алерты». `protection.
   auto-punish-enabled: false` отключает лишь кик/команды, но **сетбэки и
   отмены ударов/блоков остаются** — это прямо написано в его же
   `config.yml`. Плюс в нём `anti-esp.enabled: true` по умолчанию. Если оба
   плагина будут стоять рядом, VAC будет работать в режиме наблюдения, а
   PAC — молча откатывать и отменять. Процедура — раздел 9.
2. **Anti-ESP не проверен и по умолчанию выключен** (`anti-esp.enabled: false`).
   Anti-ESP удалённого `PurpurBedrockAC` больше не работает — я **не утверждаю**,
   что VAC его заменяет: это не проверено на клиенте. Модуль использует
   `hideEntity/showEntity`, не трогает пары, где видимостью владеет кто-то
   другой (Vanish), и не трогает игроков с открытым GUI, чтобы не подвесить
   меню на Bedrock. Включать только после теста.
3. **Внутренние классы ядра — не стабильный API.** `PurpurWorldConfig`,
   `World#getHandle().purpurConfig`, `BedrockPlaceholderHook.resolveOnline`
   читаются рефлексией. Если их переименуют, VAC не упадёт: `coreCombatEnabled`
   вернёт «включено» (не считаем частоту ударов уликой), мост устройства —
   `unknown` (мягкие лимиты). Деградация безопасная, но детект слабее.
4. **`blockreach` в текущем конфиге ядра фактически не работает:** при
   `bedrock.anti-ghost-blocks.reach-tolerance: 2.25` ядро разрешает блоки до
   ~10. Ужесточать надо в конфиге ядра, а не в античите.
5. **Нет проверок:** HitBox-расширение, пакетные Criticals, NoSlow,
   InventoryMove/ChestStealer (сознательно — меню `VoidShulker` и Java-меню
   ядра), BedFucker сквозь застройку.
6. **`Timer` ловит ускорение, но не заморозку пакетов (Blink).**
7. **Ложные срабатывания на телефоне** при `inputMode == UNKNOWN` теперь
   смягчены, но порог джиттера `spike-interval-ms: 900` может быть велик для
   мобильного канала 300–600 мс.

## 8. Что обязательно проверить на настоящем Bedrock-клиенте

1. Вход и первые 10 с (грейс) — нет Speed/Fly.
2. Телефон (тач) и ПК; телефон с клавиатурой и мышью.
3. `VoidAuthSpawn`: удержание у точки и выход из него.
4. `VoidWardenCity` (вход в данж) и дом клана `VoidClans`.
5. Бур I и II по камню — все блоки ломаются, FastBreak молчит.
6. PvP-комбо с `VoidPvP` и без него; атаки по группе мобов; копьё; MACE
   (урон −5 от VoidPvP не должен меняться).
7. Намеренный обрыв Wi-Fi на 1–3 с.
8. Лодка по синему льду; элитра с фейерверками; трезубец (Riptide).
9. Меню `VoidShulker`/кейсов и сундуки — открываются, не закрываются сами.
10. `/vac info <ник>`: устройство и пинг не `unknown` при живой Geyser-сессии.
11. **Неделя с `enforcement: false`** (только алерты), затем решение о
    включении отмен/setback. Кики и баны не включать без отдельного согласия.

## 9. `PurpurBedrockAC`: что именно проверить и как убрать

Пользователь просил проверить наличие старого плагина на живом сервере. Из этой
песочницы сервер не виден, поэтому — что искать и что делать.

### Чем он мешает (по его же исходникам и конфигу)

| Факт | Последствие |
|---|---|
| `/pac` и `/purpurac` с алиасами `anticheat`, `ac` | не конфликтует с `/vac`, но два античита одновременно |
| `protection.auto-punish-enabled: false` по умолчанию | отключает **только** кик/команды |
| `applySetback()` вызывается при `settings.setback`, который по умолчанию `meta.movementStyle()` = **включён** для движения | сетбэки и `setTo(from)` работают |
| ~10 мест `event.setCancelled(true)` в `CheckRunner` | отмены ударов и блоков работают |
| `anti-esp.enabled: true` по умолчанию | скрывает сущности и игроков |
| глобального «режима наблюдения» нет | тихого режима «только алерты» у него не существует |

Вывод: рядом с VAC он сведёт на нет весь смысл `enforcement: false`.

### Проверка наличия (сервер остановлен)

```bash
cd <каталог сервера>/plugins
ls -l PurpurBedrockAC*.jar 2>/dev/null
# конфиг и данные, если плагин уже запускался:
ls -ld PurpurBedrockAC 2>/dev/null
```

Если в списке нет — ничего не трогать, переходить к установке VAC.

### Удаление (сервер остановлен)

```bash
cd <каталог сервера>
mkdir -p plugins-disabled
mv plugins/PurpurBedrockAC*.jar plugins-disabled/
# на всякий случай — вместе с данными/конфигом:
[ -d plugins/PurpurBedrockAC ] && mv plugins/PurpurBedrockAC plugins-disabled/PurpurBedrockAC-data
ls -l plugins-disabled/
```

Не `rm`: `mv` оставляет рабочий откат. Каталог `plugins-disabled` не
загружается сервером.

### После установки VAC — проверка, что старый не вернулся

```bash
# в консоли или из чата
/vac        # должен ответить VAC, а не PAC
/pac        # должен быть "Unknown command" — значит PAC не загружен
```

Если `/pac` отвечает — JAR остался в `plugins/` или в подкаталоге;
проверить `plugins/*/PurpurBedrockAC*.jar` и логи запуска.

Отдельно: ядро **собирает** `PurpurBedrockAC-26.2.jar` в своём CI, и он может
лежать в релизе ядра. Это не значит, что его нужно ставить — наоборот.
